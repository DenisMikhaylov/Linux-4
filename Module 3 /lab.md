
## Лабораторная работа . Решение проблем с загрузчиком (GRUB)

**Цель:** Научиться диагностировать и восстанавливать загрузчик GRUB при его повреждении.

**Продолжительность:** 1,5–2 часа.

**Оборудование:** Виртуальная машина с Debian 11/12, установочный ISO-образ Debian (Live-режим) или любой Live-дистрибутив с поддержкой chroot.

---

### Теоретическая справка

- GRUB — загрузчик, который ищет свой конфигурационный файл `grub.cfg` в каталоге `/boot/grub/` (или `/boot/grub2/`).
- При загрузке GRUB считывает этот файл, показывает меню и передаёт управление выбранному ядру.
- Если файл отсутствует или повреждён, появляется приглашение `grub rescue>`.
- Восстановление требует загрузки с Live-системы, монтирования корневого раздела и переустановки GRUB.

---

### Скрипт поломки

Создайте на целевой машине скрипт `break_grub.sh` с содержимым:

```bash
#!/bin/bash
# Скрипт "ломает" загрузчик GRUB, удаляя основной конфигурационный файл

# Делаем резервную копию, если её ещё нет
if [ -f /boot/grub/grub.cfg ]; then
    sudo cp /boot/grub/grub.cfg /boot/grub/grub.cfg.backup
    echo "Резервная копия сохранена как /boot/grub/grub.cfg.backup"
fi

# Удаляем grub.cfg
sudo rm -f /boot/grub/grub.cfg
echo "Файл /boot/grub/grub.cfg удалён. При следующей загрузке GRUB перейдёт в режим rescue."
```

Сделайте скрипт исполняемым:

```bash
chmod +x break_grub.sh
```

**Выполните его от root или с sudo:** `./break_grub.sh`.

Теперь **перезагрузите** машину. После перезагрузки вы увидите приглашение `grub rescue>`.

---

### Диагностика

При загрузке появляется:

```
error: file '/boot/grub/i386-pc/normal.mod' not found.
Entering rescue mode...
grub rescue>
```

Это означает, что GRUB не может найти свой модуль и конфигурацию.

В режиме rescue доступны команды: `ls`, `set`, `insmod`, `normal`. Попробуйте:

- `ls` — покажет доступные диски и разделы (например, `(hd0)`, `(hd0,msdos1)` и т.д.).
- Определите, на каком разделе находится `/boot` (обычно это `(hd0,msdos1)` или `(hd0,gpt2)`).
- Попробуйте вручную загрузить систему, указав ядро и initrd, но это сложно. Поэтому мы перейдём к восстановлению через Live-систему.

---

### Восстановление

1. **Загрузитесь с Live-USB** (Debian Installer в режиме Rescue или любой Linux Live).
2. Откройте терминал (от root).
3. **Определите разделы** с помощью `lsblk` или `fdisk -l`.
   - Найдите корневой раздел (обычно самый большой, ext4).
   - Если `/boot` вынесен отдельно, запомните и его.
   - Для UEFI также нужен раздел EFI (vfat).
4. **Смонтируйте корневую файловую систему**:
   ```bash
   mount /dev/sdX4 /mnt   # замените sdX4 на ваш корневой раздел
   ```
5. **Смонтируйте /boot, если он отдельный**:
   ```bash
   mount /dev/sdX3 /mnt/boot
   ```
6. **Для UEFI смонтируйте EFI-раздел**:
   ```bash
   mount /dev/sdX2 /mnt/boot/efi
   ```
7. **Привяжите системные каталоги**:
   ```bash
   mount --bind /proc /mnt/proc
   mount --bind /sys /mnt/sys
   mount --bind /dev /mnt/dev
   ```
8. **Перейдите в окружение chroot**:
   ```bash
   chroot /mnt /bin/bash
   ```
9. **Переустановите GRUB**:
   - Определите режим: `[ -d /sys/firmware/efi ] && echo UEFI || echo BIOS`.
   - Для BIOS:
     ```bash
     grub-install /dev/sdX      # где sdX — диск (например, sda), а не раздел
     ```
   - Для UEFI:
     ```bash
     grub-install --target=x86_64-efi --efi-directory=/boot/efi
     ```
10. **Сгенерируйте новый конфигурационный файл**:
    ```bash
    update-grub
    ```
11. **Выйдите из chroot**:
    ```bash
    exit
    ```
12. **Размонтируйте все** и перезагрузитесь:
    ```bash
    umount -R /mnt
    reboot
    ```

После перезагрузки система должна загрузиться в обычном режиме.

---

### Проверка

Убедитесь, что файл `/boot/grub/grub.cfg` восстановлен и меню GRUB отображается.

---

### Контрольные вопросы

1. Как определить, используется ли UEFI или BIOS?
2. Какие разделы нужно смонтировать при восстановлении GRUB через Live-систему?
3. В чём отличие установки GRUB для BIOS и UEFI?
4. Что такое `chroot` и зачем он нужен?
5. Как проверить, что GRUB установлен успешно?

---

### Скрипт автоматического восстановления (для преподавателя)

Можно создать скрипт `fix_grub.sh`, который выполнит все шаги в chroot. Однако для учебных целей студент должен пройти шаги вручную.

## Лабораторная работа №2. Восстановление повреждённого ядра

**Цель:** Научиться восстанавливать систему при повреждении файлов ядра или initramfs.

**Продолжительность:** 1,5–2 часа.

**Оборудование:** Та же ВМ, Live-ISO.

---

### Теоретическая справка

- Ядро Linux находится в `/boot/vmlinuz-<версия>`, initramfs — `/boot/initramfs-<версия>.img`.
- При отсутствии этих файлов GRUB выдаст ошибку `file not found`, либо ядро не сможет смонтировать корневую ФС (kernel panic).
- Восстановление возможно путём переустановки пакета с ядром или перегенерации initramfs.

---

### Скрипт поломки

Создайте скрипт `break_kernel.sh`:

```bash
#!/bin/bash
# Удаляет файлы текущего ядра и initramfs из /boot

# Определяем текущее ядро
KERNEL=$(uname -r)

# Резервное копирование (на всякий случай)
if [ -f /boot/vmlinuz-${KERNEL} ]; then
    sudo cp /boot/vmlinuz-${KERNEL} /boot/vmlinuz-${KERNEL}.backup
fi
if [ -f /boot/initramfs-${KERNEL}.img ]; then
    sudo cp /boot/initramfs-${KERNEL}.img /boot/initramfs-${KERNEL}.img.backup
fi

# Удаляем файлы
sudo rm -f /boot/vmlinuz-${KERNEL}
sudo rm -f /boot/initramfs-${KERNEL}.img

echo "Файлы ядра и initramfs для версии ${KERNEL} удалены."
echo "При загрузке GRUB покажет ошибку 'file not found'."
```

Выполните скрипт и перезагрузитесь.

---

### Диагностика

После перезагрузки вы увидите меню GRUB, но при выборе вашего ядра появится ошибка:

```
error: file '/vmlinuz-...' not found.
error: you need to load the kernel first.
```

Нажмите `e` для редактирования пункта меню, проверьте пути. Ядра нет. Если у вас установлено несколько ядер, выберите другое (если оно есть). В противном случае придётся загружаться с Live-системы.

---

### Восстановление

**Способ 1. Через режим восстановления (если есть другое ядро)**

- В меню GRUB выберите "Advanced options" и загрузитесь с другим ядром (если оно существует).
- После входа в систему установите повреждённое ядро заново:
  ```bash
  sudo apt update
  sudo apt install --reinstall linux-image-$(uname -r)
  sudo update-initramfs -u -k $(uname -r)
  sudo update-grub
  ```
- Перезагрузитесь.

**Способ 2. Через Live-систему (если нет запасного ядра)**

1. Загрузитесь с Live-USB.
2. Смонтируйте корневой раздел и `/boot` (если отдельный) в `/mnt`.
3. Привяжите `/proc`, `/sys`, `/dev`.
4. Выполните `chroot /mnt`.
5. Проверьте, какие пакеты ядра установлены:
   ```bash
   dpkg -l | grep linux-image
   ```
6. Установите последнее доступное ядро (или переустановите текущее). Например, для Debian:
   ```bash
   apt install --reinstall linux-image-amd64   # или конкретную версию
   ```
   Если не получается, установите новое ядро:
   ```bash
   apt install linux-image-$(uname -r)   # не сработает, так как uname выдаёт версию Live-системы
   # Лучше посмотреть доступные версии:
   apt search linux-image
   apt install linux-image-5.10.0-...   # выберите подходящую
   ```
7. Перегенерируйте initramfs для всех ядер:
   ```bash
   update-initramfs -u -k all
   ```
8. Обновите GRUB:
   ```bash
   update-grub
   ```
9. Выйдите из chroot, размонтируйте и перезагрузитесь.

---

### Проверка

Убедитесь, что в `/boot` появились файлы `vmlinuz-*` и `initramfs-*.img`, и система загружается.

---

## Лабораторная работа №3. Решение проблем с systemd

**Цель:** Научиться диагностировать и исправлять ошибки инициализации, вызванные проблемами в systemd.

**Продолжительность:** 1,5–2 часа.

**Оборудование:** ВМ Debian, Live-ISO (может не понадобиться, так как можно загрузиться в emergency/rescue mode).

---

### Теоретическая справка

- systemd — первый процесс (PID 1), запускает все службы последовательно или параллельно.
- При ошибке в файле `/etc/fstab` система может перейти в emergency mode.
- Неправильный юнит-файл может привести к зависанию загрузки (например, служба, которая никогда не завершается).
- Для восстановления можно войти в emergency или rescue mode через GRUB, исправить файлы и перезагрузиться.

---

### Скрипт поломки (вариант 1 – ломаем fstab)

Создайте скрипт `break_fstab.sh`:

```bash
#!/bin/bash
# Добавляет несуществующий раздел в /etc/fstab, что вызовет emergency mode

# Резервируем fstab
sudo cp /etc/fstab /etc/fstab.backup

# Добавляем строку с несуществующим устройством
echo "/dev/sdX99 /mnt/nonexistent ext4 defaults 0 0" | sudo tee -a /etc/fstab

echo "В /etc/fstab добавлена неправильная запись. При загрузке система перейдёт в emergency mode."
```

Выполните и перезагрузитесь.

---

### Диагностика

При загрузке появится сообщение:

```
You are in emergency mode. After logging in, type "journalctl -xb" to view system logs, "systemctl reboot" to reboot, "systemctl default" to try again to boot into default mode.
```

Введите пароль root и войдите.

**Проверка:** `journalctl -xb` покажет ошибку монтирования `/dev/sdX99`.

---

### Восстановление (для fstab)

1. В emergency mode смонтируйте корневую ФС для записи (она уже смонтирована как read-only):
   ```bash
   mount -o remount,rw /
   ```
2. Отредактируйте `/etc/fstab` и удалите ошибочную строку (или закомментируйте её).
3. Сохраните файл и перезагрузитесь:
   ```bash
   systemctl reboot
   ```

---

### Скрипт поломки (вариант 2 – сломанный сервис)

Создайте скрипт `break_service.sh`:

```bash
#!/bin/bash
# Создаёт сервис, который никогда не завершается, и включает его в автозагрузку

sudo tee /etc/systemd/system/bad.service <<EOF
[Unit]
Description=Bad service that hangs forever
After=network.target

[Service]
ExecStart=/bin/bash -c "while true; do sleep 10; done"
Restart=always

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable bad.service
echo "Сервис bad.service создан и включён. При загрузке он будет висеть бесконечно, но не должен блокировать загрузку (если не имеет Type=idle или не мешает другим службам). Однако если он будет иметь Type=oneshot с RemainAfterExit=no, может заблокировать. Для надёжной поломки создадим сервис с Type=oneshot, который никогда не завершается."
```

Более надёжная поломка — создать сервис с `Type=oneshot` и бесконечным циклом, тогда systemd будет ждать его завершения и загрузка зависнет.

Изменим скрипт:

```bash
sudo tee /etc/systemd/system/bad.service <<EOF
[Unit]
Description=Bad service that never exits

[Service]
Type=oneshot
ExecStart=/bin/bash -c "while true; do sleep 10; done"
RemainAfterExit=no

[Install]
WantedBy=multi-user.target
EOF
```

После включения и перезагрузки загрузка зависнет на сообщении `A start job is running for bad.service`.

---

### Диагностика (для сломанного сервиса)

При зависшей загрузке можно переключиться на другой tty (Ctrl+Alt+F2) или перезагрузиться, выбрав в GRUB режим восстановления (recovery mode) и затем `root` для получения оболочки.

В recovery mode система загрузится в минимальном окружении, не дожидаясь завершения проблемного сервиса.

---

### Восстановление (для сломанного сервиса)

1. Загрузитесь в recovery mode (выберите в GRUB пункт `(recovery mode)` и затем `root`).
2. Отключите проблемный сервис:
   ```bash
   systemctl disable bad.service
   ```
3. Удалите файл юнита:
   ```bash
   rm /etc/systemd/system/bad.service
   ```
4. Перезагрузитесь:
   ```bash
   systemctl reboot
   ```

Если recovery mode недоступен, можно загрузиться с Live-системы, смонтировать корневой раздел, удалить файл юнита и отключить его через `chroot`.

---

### Проверка

После восстановления система должна загружаться нормально.
